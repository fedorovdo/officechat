## Интерфейс: подтверждённый объём

Пользователь подтвердил появление управления удалением. На предоставленном
скриншоте выбран возрастной режим со сроком 10 дней, одна копия отмечена,
открыт предпросмотр возрастной очистки: обычные старые копии помечены как
кандидаты удаления, защищённые — как сохраняемые. Флажок включения защищённых
копий в ручной предпросмотр выключен.

Первый скриншот сам по себе не подтверждал сохранение срока 10 дней или
выполнение очистки. Возрастной предпросмотр относится к политике хранилища,
а выбор строк — к отдельному ручному удалению.

16.10.2026 пользователь сообщил: копии удаляются успешно, срок изменён на
2 дня для наблюдения фактической автоочистки. На следующем скриншоте видны
режим «По возрасту копий», значение 2, расположение ручного удаления
«В обоих хранилищах» и отсутствие выбранных строк. Это подтверждает сообщение
пользователя о ручном удалении и выбранный в интерфейсе срок; конкретные ID,
число удалённых копий и проверка их отсутствия в каждом хранилище не присланы.
Все варианты ручного удаления пока не считаются пройденными.

На втором скриншоте включён флажок добавления защищённых копий в ручной
предпросмотр. Он не меняет защиту от автоматической очистки. Сохранение
возрастной политики не запускает удаление немедленно: очистка выполняется
после успешного бэкапа. Два дня означают 48 часов по UTC-времени в ID архива;
защищённые и последняя проверенная копия каждого хранилища сохраняются.
Фактический результат автоматической очистки ещё не получен.

## 19 октября: дефект отображения сохранённого срока

На трёх свежих скриншотах Debian интерфейс показывает режим GFS. В списке
присутствуют успешные плановые копии за 17–19 октября под RC13.39, локально
и на SMB; ручные копии от 16 октября также остаются. Более ранние скриншоты
за 16 октября позволяют сравнить состав. Эти данные подтверждают плановые
копии, но не подтверждают работу возрастного удаления за 2 дня.

Обнаружена воспроизводимая ошибка RC13.39: `_parse_simple_config()` в
`scripts/backup_agent.py` не включает `RETENTION_MODE` и `RETENTION_DAYS`
в список читаемых ключей. Поэтому status всегда возвращает `gfs` и `30`,
даже если в backup.conf записаны другие значения. Интерфейс получает эти
значения при открытии страницы. Чтение status не переписывает backup.conf;
фактический режим на VM нужно проверить отдельно, прежде чем утверждать,
что сохранение сбросилось либо возрастная очистка работала.

Локально подготовлено исправление списка ключей и регрессионные тесты
повторного чтения status новым экземпляром агента для days/2, disabled/7,
gfs/45, а также старого конфига без новых ключей. Исправление впоследствии
доставлено на Debian точечно, но ещё не опубликовано в релизе.

Диагностика Debian 19.10.2026: `RETENTION_DIAGNOSTICS=PASS`, exit `0`.
В backup.conf фактически записано `RETENTION_MODE=days`, `RETENTION_DAYS=5`.
История содержит успешное сохранение days/5 от
`2026-10-16T18:24:47.508984+00:00` (21:24:47 MSK), без error_code.
Таким образом, подтверждённый сохранённый срок — 5 дней; прежний выбор
2 дней в форме не является доказательством его сохранения. Наличие обычных
копий от 16 октября на 19 октября этому сроку соответствует. Возврат
конфига к значениям по умолчанию диагностикой не подтверждён.

Пользователь применил точечное исправление на Debian:
`DEBIAN_RC13_39_RETENTION_STATUS_FIX=PASS`, exit `0`, агент active,
backup.conf прошёл проверку неизменности. Исходный файл сохранён в
`/root/officechat-retention-status-fix.XgJBWL`.
На скриншотах после перезапуска UI сообщает о недоступности агента;
поля хранилища/таймера/срока показывают значения при ошибке загрузки.
Это не подтверждает сброс настроек или отключение NAS. Проверяется связь
host ↔ backend: каталог сокета примонтирован в backend, а systemd-unit
без RuntimeDirectoryPreserve может пересоздать его при рестарте агента.
Состояние действующего mount и timer, связь через socket с обеих сторон
и отображение days/5 после восстановления связи требуют подтверждения.

Последующая проверка: `DEBIAN_BACKUP_AGENT_CONNECTION=PASS`, exit `0`,
каталог `/root/officechat-agent-connection.CPv0R8`.
На host status сразу доступен, а из backend получен FileNotFoundError.
После рестарта только `officechat-backend-1` status из контейнера доступен:
`BACKEND_AGENT_RECONNECTED=PASS`. С обеих сторон получены days/5, timer
installed/enabled/active=true и offsite configured/required/mounted=true,
status=copied. Реальный mount — прежний SMB OfficeChatDebianRc36.
backup.conf и settings/current.json прошли проверку неизменности.
Ближайший запуск: 20.10.2026 02:30 MSK; последний — 19.10.2026 02:30:10 MSK.
Таким образом, потеря связи host ↔ backend после рестарта агента устранена;
сброс настроек хранилища/расписания не подтверждается. В исходном unit
локально добавлено RuntimeDirectoryPreserve=yes для сохранения каталога,
примонтированного в backend. Эта часть исправления на VM пока не установлена.

## 24 октября: ночные копии и автоматическая очистка Debian

Источник — предоставленные пользователем скриншоты и полный вывод
`journalctl -u officechat-backup.service` вместе с `status` и всеми страницами
`list_backups`, полученными через клиент агента внутри действующего backend.

- Все запуски 20–24 октября в 02:30 MSK завершены успешно за 8–9 секунд.
  Каждый журнал содержит проверку локального и SMB экземпляров и завершение.
- 21 октября из обоих хранилищ удалены ID от 14 и 15 октября UTC;
  22 октября — четыре расходные копии от 16 октября UTC;
  23 октября — ID `officechat-backup-20261017-233011Z`;
  24 октября — ID `officechat-backup-20261018-233011Z`.
  Журнал `Rotating old backup` и отсутствие этих ID в полном списке
  подтверждают фактическую очистку, а не только предпросмотр.
- Остались пять незащищённых проверенных копий за 20–24 октября MSK
  (UTC ID от `20261019-233011Z` до `20261023-233011Z`), каждая local/offsite.
- Сохранились защищённые ID `20261016-122420Z`, `20261015-075834Z`,
  `20261013-184954Z` в обоих хранилищах и `20261013-180440Z` только локально
  (все с префиксом `officechat-backup-`, verification passed).
- Status: backup_health=healthy, last_run.success=true,
  offsite.status=copied, mounted=true, warnings=[];
  retention.mode=days, retention.days=5. Таймер enabled/active,
  следующий запуск 25 октября 02:30 MSK.

## 24 октября: постоянное исправление runtime-каталога на Debian

Оператор выполнил процедуру
[backup-agent-runtime-fix_RU.md](../deployment/backup-agent-runtime-fix_RU.md).
Каталог диагностики на VM: `/root/officechat-socket-fix.vVFHnJ`.
Результаты: `AGENT_RESTART_1=PASS`, `AGENT_RESTART_2=PASS`,
`BACKUP_AGENT_RUNTIME_FIX=PASS`.

- Установлен systemd drop-in

  с RuntimeDirectoryPreserve=yes; после daemon-reload свойство проверено.
- Два рестарта агента сохранили device/inode runtime-каталога,
  container ID и StartedAt действующего backend; backend не перезапускался.
- После каждого рестарта запрос status из backend успешен: agent available,
  backup healthy, days/5, timer enabled/active, offsite mounted/copied,
  warnings=[]. Следующий запуск 25 октября 02:30 MSK.
- SHA-256 backup.conf, backup-agent.conf и `/opt/officechat/.env` до/после
  совпали. Значение «ЦЕЛ» в выводе sha256sum означает успешную проверку.

Исправления чтения retention и сохранения runtime-каталога должны войти в
следующий release bundle. Drop-in переживает reboot, но сам `/run` является
временной файловой системой; полный reboot после этой правки ещё не проверен.
