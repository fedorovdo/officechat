# OfficeChat 0.1.0 — проект выпуска для первого рабочего пилота

Статус: подготовка исходников. Тег `v0.1.0`, новые образы и установочные assets
ещё не опубликованы. Документ не является командой устанавливать несуществующий
релиз. Подтверждённые результаты и оставшиеся проверки находятся в
[журнале приёмки](0.1.0-readiness_RU.md#обновление-приёмки-15-ноября-2026).

## Состав

База — опубликованный `v0.1.0-rc14`, commit
`620334c8d178bb0ef7567430ba2766d68817fc10`. Сохраняются возможности RC14,
исправления чтения политики хранения и каталога сокета backup-agent.

Изменение установки: обычный standalone installer устанавливает SMB/NFS mount
helpers (`cifs-utils` и клиент NFS) из репозиториев ОС после проверки доступа
к образам. Это работает и при уже установленном Docker. С
`--no-install-docker` пакеты ОС не устанавливаются. Подключение NAS и включение
расписания по-прежнему выполняются администратором.

Новых миграций нет; Alembic остаётся `20261014_0027`.

## Выпуск после приёмки

1. Зафиксировать успешные restore/reboot и установку с mount helpers в журнале.
   Проверить применимые пункты RELEASE_CHECKLIST_RU.md и ограничения issue #10.
2. Выполнить workflow Release Images на ветке `release/0.1.0` с
   `version=0.1.0`, `ghcr_access_preflight_only=true`, `push_rc_tag=false`.
   Этот запуск проверяет CI и доступ к GHCR без публикации образов и assets.
3. При успешной приёмке объединить подготовленные изменения обычным merge,
   сохранив историю; убедиться, что итоговый commit содержит RC14 и эту правку.
   Зафиксировать точный SHA. Не собирать прежнюю отстающую main.
4. Создать annotated tag `v0.1.0` на проверенном итоговом SHA. Workflow тега
   выполняет полные тесты и публикует versioned images. Сборка после merge
   должна пройти заново; branch preflight не заменяет проверку тега.
5. Скачать артефакт успешной сборки тега. Проверить installer, bundle и
   image-digests SHA-256, все внутренние checksums, version/revision и digests.
6. Создать GitHub Release с шестью файлами из **этой** сборки. Заменить проект
   release notes фактическими SHA, ссылкой CI и подтверждёнными ограничениями.
   Проверить публичные download URL. После этого использовать версию `0.1.0`
   по [INSTALL_RU.md](../INSTALL_RU.md).

## Новый рабочий сервер

Выбран новый чистый сервер; тестовая VM `192.168.0.94` остаётся стендом.
До установки нужны IP, постоянное DNS-имя, snapshot и проверка ресурсов.
Данные тестового чата не переносятся без отдельной задачи переноса.

Сначала выполнить проверенную установку конкретного опубликованного выпуска,
настроить доверие CA клиентов, создать тестовых пользователей и проверить
сообщения и вложения. Для рабочего NAS использовать отдельную папку, затем
создать и проверить внешнюю копию, включить расписание и проверить reboot.
Допуск сотрудников — после этих проверок.

Приватные конфигурация и ключи CA по умолчанию не входят в plaintext-копию
на NAS; обеспечить их отдельное защищённое хранение согласно
[BACKUP_RESTORE_RU.md](../BACKUP_RESTORE_RU.md).
