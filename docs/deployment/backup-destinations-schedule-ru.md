# Хранилище резервных копий и расписание

Статус: реализация в ветке `feat/backup-destinations-schedule`. Код и локальные тесты подготовлены; монтирование, расписание и восстановление с NAS ещё нужно проверить на тестовых Debian 13 и RED OS 8 до установки на рабочий сервер.

### Настройка в интерфейсе

1. В разделе «Резервные копии» суперадминистратор выбирает NFS или SMB, вводит сервер и export/общий ресурс. Для SMB также указывает отдельную учётную запись, пароль и при необходимости домен AD. NFS использует права экспорта, без логина и пароля.
   Если для SMB нужна папка внутри общего ресурса, укажите её отдельно от имени ресурса, например сервер `192.168.1.100`, ресурс `backup_share`, папка `OfficeChat` для `//192.168.1.100/backup_share/OfficeChat`. Папка должна существовать и быть доступной на чтение и запись учётной записи резервного копирования. Пустое поле папки означает корень ресурса; обратные косые черты в поле папки не используются.
2. Сервер подключает ресурс к `/mnt/officechat-offsite`, делает пробную запись, а затем записывает `OFFSITE_ROOT` в `/etc/officechat/backup.conf`. Пароль SMB хранится в `/etc/officechat/backup-offsite.credentials` с режимом `0600`; API возвращает только имя сервера и общего ресурса.
3. Создайте ручную копию. Убедитесь, что статус внешней копии — `copied`, а проверка прошла. Проведите `restore-drill`, включая внешний экземпляр, на тестовой машине.
4. Выберите дни и время по часовому поясу сервера, включите автоматические копии. Таймер активируется только после проверенной копии в выбранном хранилище.

Для NFS на Debian нужен пакет `nfs-common`, на RED OS — `nfs-utils`. Для SMB нужен `cifs-utils`. При отсутствии пакета интерфейс сообщает о нём; установить его нужно на сервере один раз. Технический журнал операции: `journalctl -u 'officechat-backup-settings@*' --no-pager`.

Первая версия позволяет добавить одну внешнюю площадку. Смена и отключение уже настроенного NAS выполняются вручную на сервере как отдельная миграция; старые копии не удаляются. Параметры хранения (14/8/12) пока задаются в `backup.conf`, интерфейс показывает их только для чтения.

## Разделы интерфейса

- **Резервные копии**: место второй копии, проверка подключения, расписание, дата следующего запуска, результат последней копии и её восстановления. Настройки меняет только суперадминистратор. Оператор с `can_restore_backup` может их просматривать, но не менять.
- **Управление хранилищем**: объём пользовательских вложений и политика хранения сообщений/файлов. Кнопка подключения NFS/SMB здесь не нужна. Добавлен показ ёмкости и свободного места раздела, на котором расположены вложения.

## Места копирования

Каждый запуск сначала создаёт и проверяет локальную копию. После этого копирует её на выбранную внешнюю площадку и проверяет внешнюю копию. Нельзя выбирать «только на NFS/SMB»: сетевой сбой не должен лишать сервер локальной копии. Интерфейс явно показывает `copied`, `skipped_not_mounted` либо `failed`, а также настройку `REQUIRE_OFFSITE`. Для рабочего сервера включать обязательную внешнюю копию после успешного теста доступности и восстановления. Отсутствие сетевого mount не должно превращаться в запись в незаметный локальный каталог.

Поддержать одну активную внешнюю площадку на первом этапе:

| Вариант | Данные администратора | Проверки |
| --- | --- | --- |
| Локально | Уже установленный каталог `/var/backups/officechat/production` | Свободное место, запись, защищённая копия. |
| NFS | Сервер, export, отдельная точка mount на хосте | Доступность, действительный mount, запись от root и чтение, другая файловая система относительно локальной копии. Обычный NFS с `sec=sys` не имеет поля «логин/пароль»; Kerberos требует отдельной настройки сервера и клиента. |
| SMB/CIFS | `//сервер/ресурс`, отдельная учётная запись (в том числе доменная), пароль | Учётные данные только в root-owned файле `0600` на хосте; пароль не показывать через API, не записывать в URL, командную строку, журналы или `backup.conf`. Проверять mount, запись/чтение и место. |

Ручная настройка через SSH сейчас возможна посредством `OFFSITE_ROOT` в `/etc/officechat/backup.conf`. Браузерный редактор требует ограниченного протокола для привилегированного агента; backend в контейнере не должен монтировать файловые системы. Не принимать произвольную команду, параметры mount или произвольную точку mount из браузера. Разрешить только выделенный каталог, например `/mnt/officechat-backups/<id>`, и структурированные поля NFS/SMB. Прежде чем сохранять конфигурацию, проверять mount и пробную запись; атомарно сохранять файлы и оставлять прежнюю работающую конфигурацию при ошибке. После перезагрузки mount должен восстанавливаться. При изменении или удалении площадки никогда не удалять уже созданные копии.

Скрипт уже исключает незашифрованные приватные архивы из внешней копии по умолчанию. Интерфейс должен объяснять, что для переноса чата на другой сервер потребуются также секреты приложения и Caddy CA. Перед включением отправки приватных архивов на NAS следует отдельно настроить `age` и проверить восстановление на другой ВМ.

## Автоматические копии

На экране «Резервные копии» показать включение таймера, дни недели, локальное время сервера, время запуска, фактический следующий запуск, срок хранения и результат последнего автоматического запуска. Первый вариант: ежедневно либо выбранные дни недели и одно время; календарь для выбора отдельных дат пока не требуется. Применять расписание через drop-in `officechat-backup.timer` с ограниченным валидатором полей, `systemd-analyze calendar`, `daemon-reload` и проверкой следующего запуска. При неуспехе восстановить предыдущий drop-in и состояние таймера. Текущий таймер установлен и отключён по умолчанию; обновление OfficeChat должно сохранять выбранное расписание и состояние включения.

Перед включением автоматического режима: проверить достаточное свободное место, сделать ручную копию, проверить её и провести `restore-drill` для локальной и внешней площадки. Автоматические копии запускаются существующим `officechat-backup.service --scheduled`. Не разрешать изменение настроек одновременно с backup, upgrade или restore. Все изменения и результаты проверки записывать в аудит. Пароль SMB из аудита исключить.

## Ёмкость для 300 пользователей

Точный размер задаётся привычками пользователей, а не количеством учётных записей. Ограничение сейчас: один файл до 25 МиБ, до 10 файлов в сообщении и до 50 МиБ вложений в одном сообщении; общего лимита на пользователя пока нет.

| Новые вложения на активного пользователя | Прирост у 300 пользователей | За 12 месяцев без удаления |
| --- | ---: | ---: |
| 20 МиБ/месяц | ~6 ГиБ/месяц | ~70 ГиБ |
| 100 МиБ/месяц | ~30 ГиБ/месяц | ~350 ГиБ |
| 300 МиБ/месяц | ~90 ГиБ/месяц | ~1,1 ТиБ |

Это оценка пользовательских файлов без базы данных, журналов, временного места, Docker-образов и запаса. Для начала пилота на 300 человек: отдельный системный диск 80 ГиБ и расширяемый диск данных 500 ГиБ для `/var/lib/officechat`; если документы пересылают активно, сразу выбрать 1 ТиБ для данных. Предупреждения по месту на 70/85%, пересчёт через первый месяц по фактическому приросту. Не размещать единственную копию на этом диске.

Текущие резервные копии являются полными. Политика `KEEP_DAILY=14`, `KEEP_WEEKLY=8`, `KEEP_MONTHLY=12` может сохранить до 34 разных полных копий плюс защищённые копии перед обновлением/восстановлением. Например, при среднем размере копии 100 ГиБ только 34 копии займут до ~3,4 ТиБ без учёта накладных расходов; при 350 ГиБ — до ~12 ТиБ. Ёмкость NFS/SMB нужно считать по **фактическому размеру полной копии × числу одновременно сохраняемых копий** с запасом, либо вводить инкрементальную/дедуплицируемую стратегию и заново проверять восстановление. Нельзя обещать, что хранилища в 1–2 ТиБ достаточно на год без измерений.

## Приёмка до использования на рабочем сервере

1. На Debian 13 и RED OS 8 проверить NFS и SMB, перезагрузку хоста, отсутствие mount, недоступный NAS, неверные учётные данные и отсутствие записи от root. Локальная копия остаётся проверяемой; интерфейс показывает настоящую причину и статус внешней копии.
2. Проверить включение, изменение, отключение таймера, часовой пояс и сохранность расписания после обновления. Проверить реальный автоматический запуск, метку `scheduled`, обе копии и ротацию.
3. Проверить доступ администратора с новым правом и запрет прочим пользователям. Убедиться, что пароль SMB отсутствует в API, журналах, резервной копии открытых настроек и аудите.
4. Выполнить `verify-backup` и `restore-drill` для копии на NAS, затем восстановление на отдельной тестовой ВМ. Проверить сообщения, вложения и полный комплект конфигурации/секретов для переноса.
