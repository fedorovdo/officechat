### Подготовка нового рабочего хоста: 16 ноября 2026

Новая VM 101 OfficeChat на pve4: РЕД ОС 8.0.3 Standard Server Minimal,
x86_64, 16 GiB RAM; `chat.adm.net`, IP `192.168.0.50/22`, gateway
`192.168.1.1`, DNS `192.168.1.8`, Europe/Moscow, NTP synchronized,
SELinux Enforcing. По скриншоту конфигурации — 6 vCPU, CPU host.

Системный диск sda 80 GiB: EFI 600 MiB, /boot ext4 2 GiB, / XFS 73.4 GiB,
swap 4 GiB. На sdb 200 GiB создан sdb1 XFS, примонтирован по UUID в
`/var/lib/officechat`; получен `OFFICECHAT_DATA_DISK=PASS`. Для Docker добавлен
host drop-in с RequiresMountsFor и ConditionPathIsMountPoint этого каталога.
После выключения/запуска пользователь подтвердил сохранение mount, DNS A-запись
chat.adm.net → 192.168.0.50 и активный qemu-guest-agent. Предупреждение о
несуществующем virtio-порте было до включения агента в Proxmox; после старта
агент active. Сам OfficeChat на новом хосте ещё не установлен.

Пользователь отказался от отдельного диска 1 TiB: целевое хранилище копий —
RAIDIX. Новый диск не добавлять по прежнему плану. В текущих скриптах backup
сначала создаётся и сохраняется локально, затем копируется во внешнее хранилище;
режим NAS-only не реализован. При стандартном BACKUP_ROOT локальные архивы
занимают системный раздел. До рабочего использования нужно согласовать местное
место/хранение с учётом этого ограничения; не считать внешний NAS заменой
локального repository в текущей реализации. Отдельная рабочая папка RAIDIX
ещё не задана; тестовую OfficeChatreFinalTest не использовать для production.

Подготовка `release/0.1.0` основана на точном RC14. Обычный installer теперь
добавляет SMB/NFS mount helpers из штатных репозиториев, в том числе если Docker
уже установлен; `--no-install-docker` оставляет установку пакетов оператору.
Прикладная схема не меняется (`20261014_0027`).

До публикации стабильного тега и допуска сотрудников остаются:

1. Изолированный restore-drill внешней копии RC14: **PASS**, результат выше.
   Дополнительно проверить данные и скачивание контрольного вложения
   в восстановленном изолированном экземпляре приложения.
2. Проверить reboot тестовой VM: HTTPS, агент, SMB, таймер, days/5, сообщения
   и вложения. Убедиться, что клиенты доверяют CA.
3. Выполнить полный CI и сборку **точного нового SHA**, проверить sums,
   RELEASE.json и image digests. Локальные script tests не заменяют этот CI.
   Не переназывать архив RC14 в 0.1.0.
4. Проверить изменённый installer на чистой VM, включая SMB без ручной

5. Применить остальные пункты RELEASE_CHECKLIST_RU.md. Учесть открытый

   серверные ограничения действуют. Проверить фактические лимиты и контроль

## Простая установка

Существующая точка входа — `officechat-install.sh` из GitHub Release
(исходник `scripts/release/bootstrap-linux.sh`). Он скачивает и проверяет bundle,
устанавливает Docker/Compose на поддерживаемой ОС, запрашивает пароль первого
администратора, запускает приложение и Caddy и сохраняет корневой сертификат.
Подробности и поддерживаемые ОС: [INSTALL_RU.md](../INSTALL_RU.md).

Для пилота нужен минимальный путь: DNS-имя → скачать installer и checksum →
проверить checksum → запустить с точной версией и hostname → доверить CA на
клиентах → войти. Затем настроить NAS, расписание и проверить восстановление.

Текущие GHCR-образы приватные: требуется GitHub account с доступом и
авторизация Docker с read:packages. На чистой VM installer сначала устанавливает
Docker, затем останавливается до login; после login его запускают повторно.
Это ограничение текущей «простой установки» должно быть явно указано. Изменение
видимости packages не выполняется в рамках исправления сокета.

Не использовать `latest` или команду для ещё не опубликованной версии.
Тесты скриптов с подменёнными системными командами не заменяют чистую VM.
